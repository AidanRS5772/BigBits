## Architecture

BigBits is a big-integer/big-float library optimized with inline assembly (x86-64 and ARM64) and adaptive algorithm selection.

### Layer structure

```
src/utils/       ← raw buffer arithmetic (Vec<u64> limb arrays)
src/bit_nums/    ← ergonomic number types wrapping utils
src/tests/       ← test suite (gated by #[cfg(test)] in lib.rs)
benches/         ← Criterion benchmarks
```

### Utils layer (`src/utils/`)

All algorithms operate on little-endian `u64` limb buffers (index 0 is the least significant limb). Dynamic entries use pooled `Vec<u64>` scratch storage; static entries use caller-selected `[u64; N]` stack storage.

- **`mul.rs`** — Multiplication with dynamic dispatch: schoolbook → Karatsuba → FFT (via `rustfft`) → NTT. Assembly primitives (`mul_prim_asm`, `mul_asm_x86`, `mul_asm_aarch`) handle 64×64→128-bit multiply. Also provides high/middle-product variants (`hi_mul_buf/dyn/static`, `mid_mul_buf/dyn`) that compute only a limb-range of a full product — these back the Newton-Raphson reciprocal refinement in `div.rs`. Every middle-product entry accepts exactly `long[2n-1] × short[n] → out[n]`; callers materialize any required low zero padding before invoking it. `ntt_mid_mul_static` also accepts a `long` that passes `N` by low zero limbs (a reciprocal's padded divisor window): `long = T·B^z`, so it convolves `T` at the unchanged transform size and reads the band `z` coefficients lower, bit-identical to the dynamic product. Both NTT middle products size each prime's transform for at least `2n+1` coefficients (`mid_ntt_size`): the accumulation reads two coefficients below the band, which no wrapped column may reach. Static NTT entries handle transforms larger than `N` (non-5-smooth `N`) via `ntt_chunked_convolution`, which emulates the declared transform size with rescaled sub-transforms clamped to `N`.
- **`div.rs`** — Division exposes standard quotient-only, quotient-with-remainder, reciprocal, and high quotient-only operations in dynamic and static allocation models. Quotient operations dispatch among Knuth, Burnikel-Ziegler, and Newton-Raphson; reciprocal operations dispatch directly between Knuth and Newton-Raphson and have no standalone Burnikel-Ziegler path. Forced algorithm entry harnesses live in `src/tests/test_div.rs` and `benches/`, where they compose the public preflight and prepared execution drivers; they do not live in the algorithm module.

  Division operands must be trimmed and `d` must be nonzero. Let `M = div_quotient_len(n.len(), d.len()) = n.len().saturating_sub(d.len())`. Standard `div`/`div_rem` require `q.len() >= M`, write the low `M`-limb quotient body, and return the possible structural limb at index `M`. When `q.len() > M`, that limb is stored in `q[M]`, the remaining tail is zero-filled, and the function returns zero, matching multiplication's overflow convention. Equal-width operands therefore permit an empty quotient body while returning their complete single-limb quotient. Quotient-only entries preserve both operands, and standard `div_rem` always leaves the exact remainder in `n`.

  High quotient entries `hi_div_dyn` and `hi_div_static<N>` preserve the high-window capability without a remainder variant. For `q.len() = K < M`, they return the same structural overflow and write body digits `M-K..M-1` into `q`; when `K >= M`, they delegate to standard division. High-window preflight drops irrelevant low numerator limbs and exact whole-limb divisor factors before the rigid backend. Newton-Raphson keeps its contiguous `K+1` internal quotient and bridges exact-width/high-window callers through pooled dynamic or `[u64; N]` static temporary storage; an output with an overflow slot is a direct fast path.

  Each standard call validates and prepares operands, dispatches using the logical quotient width `M+1`, and then runs a prepared driver with a quotient body of width `M`. Knuth returns its initial top estimate directly. Burnikel-Ziegler returns the top digit from its initial block while later blocks fill the body. Newton-Raphson retains its contiguous full-width core and BZ correctness fallback. Tests and benchmarks force `DivAlg` or `RcpAlg` through the same prepared drivers used by public dispatch.

  Reciprocal entries preserve `d`, and `rcp.len()` is the requested precision. For `D = d.len()`, `R = rcp.len()`, `B = 2^64`, and `X = min(floor(B^(D + R - 1) / d), B^R - 1)`, the returned approximation has numeric error strictly below `B`; the least-significant output limb is intentionally not guaranteed exact. Reciprocal drivers remove exact low-zero limb factors and retain only the high divisor window relevant to `R` (R + 1 limbs), so work does not scale with irrelevant low divisor limbs. Like every static entry, `rcp_static`/`rcp_prepared_static` assert that `d` and `rcp` each fit `N` limbs. The NR reciprocal attempt uses two internal low guard limbs and discards them, but omits the full `d * rcp` verification product and bounded final correction pass. The guard limbs and schedule parity put its work buffer and last divisor window up to 3 limbs past R; the static attempt keeps those two in `[[u64; N]; 2]` storage, caps its error bands at N (they stop a couple of limbs past p + 1), and relies on the window's limbs past N being zero padding, so static NR completes for every R ≤ N (only N ≤ 3 leaves no room for a band and retries Knuth). Division's upward-biased Knuth seed reuses `knuth_rcp_normalized` with seed 1 and an explicit increment; its quotient/remainder corrections remain exact.

  Burnikel-Ziegler still uses Knuth for its recursive base cases. Newton-Raphson division falls back to Burnikel-Ziegler when estimation or bounded correction fails; the prepared reciprocal driver falls back to Knuth when refinement or normalization cannot produce a usable approximation, or when a tiny static N leaves no room for an error band. These are correctness fallbacks, not top-level performance dispatch.

  The public dispatchers are `div_dyn`, `div_rem_dyn`, `hi_div_dyn`, `rcp_dyn`, and their static counterparts. Standard and high quotient operations use `DIV_KNUTH_CUTOFF` for the mandatory Knuth region, independently of the recursive `BZ_CUTOFF`. Division selection measures the effective rigid divisor width after its exact low-zero limb factor. When its cost model selects BZ, or the requested shape cannot enter NR, it calls Knuth directly at widths up to `BZ_CUTOFF` and BZ above it; its dynamic and static BZ-vs-NR cost models remain separately tunable. Reciprocal selection depends only on `R = rcp.len()` and switches directly from Knuth to NR after `DYN_RCP_KNUTH_NR_CUTOFF` or `STATIC_RCP_KNUTH_NR_CUTOFF`. Number-type callers allocate the quotient or reciprocal buffer and call one of these entries directly; there are no allocating `div_vec`/`div_arr` adapters.

  The low-level building blocks remain `div_prim`/`div_buf_of` for normalized Knuth division, `div_2_1`/`div_3_2` for Burnikel-Ziegler recursion, and the shared `nr_err_band`/`nr_refine_rcp`/`nr_rcp_chain`/`nr_refine_quo` correction pipeline for Newton-Raphson. Four prepared division drivers apply operand windows, attempt NR, and explicitly retry through BZ on failure before preparing classical storage. NR attempts report success or failure and preserve the numerator on failure; remainder correction commits only after success. Two reciprocal drivers similarly own the NR/Knuth choice and retry. Dynamic drivers provide `ScratchGuard` buffers; static drivers provide `[u64; N]` buffers. Only shared arithmetic kernels accept multiplication callbacks.
- **`bin_split.rs`** — Binary splitting for BBP, Engel and Hyper series, each with a dynamic (exact `Vec`) and a static (`[u64; N]`, low bits dropped) node. Each kind also has a wide trait (`WideBBPSeries`, `WideEngelSeries`, `WideHyperSeries`) whose `p`/`q`/`r` return u128 and, like `neg`, take a u128 index: every narrow series is a wide one through a blanket impl (which narrows the index back, as the tree's indices are u64), and the nodes are bounded on the wide traits. A leaf whose values all fit u64 runs the narrow kernel unchanged through the `Narrow<S>` view (for a narrow series that check is a constant), and any other leaf a wide kernel that takes one term per step, with `mul_prim2` and two-limb carries (`push_or_drop2`, `add_term_wide`). A type implements one of the two traits, and calling `p`/`q` on a concrete narrow series with both in scope needs `<T as BBPSeries>::q`. `bin_split`/`bin_split_tree` take no cutoff: a tree splits `[a, b)` while it has more than `Node::LEAF_TERMS` terms and `Node::limbs` (an O(1) estimate of the node's largest part, capped at N for static nodes) is at least `Node::LEAF_LIMBS`. The parallel split compares the same estimate with `DYN_BIN_SPLIT_PAR_CUTOFF`, and only on a pool of two or more threads. Limbs replace the old per-caller term counts because bits per term vary by orders of magnitude between series. Hyper also keeps a term floor, because a wide x makes each leaf step a full multiplication. `bin_split_tree_at` takes explicit `SplitCutoffs` for tests and `benches/bin_split_cutoffs.rs`. See `docs/bin_split_cutoff_tuning.md`. `Node::finalize(ctx, zeros, out)` writes S·2^(64(out.len() + zeros)), skipping `zeros` leading limbs the caller knows are zero, so a small value deep below 1 costs only its significant limbs. Dynamic nodes finalize with `ratio_to_fraction_dyn` (one `div_dyn` sized by the output), static ones with `ratio_to_fraction_static` (a reciprocal and a high product, since that division's numerator wouldn't fit N). Static finalize takes a (len + 2)-limb reciprocal, whose error below one of its limbs costs out under 1 ulp, and requires `out.len() + 2 <= N`; at `N − 2` that reciprocal is N limbs, which `rcp_static` handles through NR. Its high product's overflow limb has no slot once y has len + 2 limbs, where S < 1 makes it zero. Static parts (P, Q, R) are `m · 2^e` with `m` in N limbs and `e` a bit exponent: exact while they fit, and afterwards their top 64N bits (P within two bits of that, and leaf parts keep one spare bit once they drop, so a term can go in over several passes). BBP keeps separate P and Q exponents like Engel and Hyper, so Q no longer carries 2^(shift·t). A merge computes P's exponent from its operands' bit lengths before any product (`p_exponent`), and each product only down to it (`product_at`/`hi_mul_from`); Q and R are normalized to their top bit (`hi_mul_norm`). A node loses at most about 11 bits below 64N (`test_static_nodes_keep_bits`), so static and dynamic finalize agree within 1 ulp all the way to finalize's `N − 2` bound; with limb exponents a node lost up to 3 limbs and was off by up to 2^63 ulps there. The last x-leaf of a sum keeps its running term t only from P's exponent up, since it never becomes R. Each static node's `ratio(ctx)` gives (P, Q, shift) with S = P / (Q·2^shift), which `finalize` and `ln2_static` divide. See the static section of `docs/bin_split_cutoff_tuning.md` for the cost. The Hyper x-leaf multiplies by x before each term, so a Hyper node sums x^(n−a+1) as `HyperSeries`'s formula states, and its R product for merges is unchanged.
- **`trans.rs`** — `exp_dyn(x, m: i64, out)` is the public e^X, with X = 2^(64m)·x and x's last limb worth 1. Top zero limbs fold into m, computed in i128, and x = 0 gives 1. It writes o = e^X / 2^(64k) ∈ [1, 2^64), with `out`'s top limb as o's integer part, and returns k. It returns `Err(ExpError::Overflow)` once k = n / 64 would pass i64::MAX (n ≥ 2^69, X ≳ 22.18·2^64), and returns it early when X ≥ 23·2^64. `exp_static::<N>` is its stack-only twin and needs `N >= out.len() + 3` (`out.len() + 4` once ln(2)'s out.len() + 2 limbs pass `ln2.bin`'s 1024, because it then sums them, without `ln2_static`'s own guard limb, through `ln2_static_unguarded`). A smaller N is a limit of the stack buffers, not an arithmetic failure, so it returns `Err(ExpError::Capacity(CapacityError { min_n }))` (checked before any input, leaving `out` untouched) instead of panicking; `CapacityError` lives in `utils/mod.rs`, and `exp_static_entry` and `ln2_static` return it too. `exp_static` takes the squares below only when N leaves room for the core at their frame's fs limbs (N ≥ fs + 3, so from out.len() + 4 while j ≤ 60), as they are only an optimization. `exp_dyn_at`/`exp_static_at` take the square count explicitly for tests and `cargo bench-bin-split exp`. Both are thin wrappers over `exp_reduced`, which takes the ln(2), division-with-remainder, core and high-square functions as `fn` pointers, like `exp_combine`'s `hi_mul`, plus three caller-provided buffers: pooled scratch for the dynamic path, `[u64; N]` arrays for the static one. Argument reduction is one exact division with remainder (`div_rem_dyn`/`div_rem_static`) of floor(X·2^(64F))·2^g by floor(ln 2·2^(64F + g)) (out.len() + 2 limbs of ln(2) shifted right by 64 − g), with F = out.len() + 1 and g = `EXP_RED_GUARD_BITS` (58). The quotient is n, at most 3 limbs, so the division is linear in F; the remainder, shifted back down by g, is r ∈ [0, ln 2) at F limbs, and out = e^r << (n mod 64). Only r's absolute error matters, and it is up to n times ln(2)'s truncation error, so ln(2) needs about 7 bits past F limbs for n < 2^69: one whole guard limb is not enough (with n mod 64 near 63 it costs ~16 ulps), and g = 58 leaves a wide margin. X's own truncation at F limbs is not multiplied by n. Guard bits instead of a second guard limb keep the numerator in out.len() + 3 limbs, since X < 23·2^64 has at most 69 integer bits. Before the core, r is scaled to r·2^-j, exactly, by a shift into xr's spare limb. j is `DYN_EXP_SQR_BITS`/`STATIC_EXP_SQR_BITS` (24; 0 disables it) less r's own leading zero bits (`exp_sqr`), and 0 when the core would sum r's chunks in parallel (`exp_par`, which applies the entries' own gate, `exp_dyn_par`/`exp_static_par`, to their frame from `exp_frame`): the squares run serially, while the series they shorten would overlap. End to end, the best j hardly moves with precision (about 24 from 1 to 16384 limbs on one thread), so it is a constant: a multiple of log2 of the precision fit worse. The core then gives u = e^(r·2^-j) − 1 in a fixed frame of fs = out.len() + ⌈(j + 4)/64⌉ fraction limbs, and `exp_square` squares it back j times as u ← 2u + u² = (1 + u)² − 1 through `hi_sqr_dyn`/`hi_sqr_static`, reusing ln(2)'s buffer for the product. It never forms 1 + u, so the frame keeps u's low bits. Each square at most doubles the error below it and adds about a unit, and ∏(1 + uᵢ) < 2, so the j + 4 extra bits keep the total under a quarter of a unit of the out.len()-limb result. u < 1/2 before the last square, and on the last one only rounding can carry past 1, which saturates as in `exp_combine`. The core runs at fs − z limbs with the squares, and at out.len() − z limbs without them (j = 0), where z is its predicted leading zero limbs. The shift by n mod 64 < 64 moves only part of its last limb into `out`, and the core's own guard limb keeps that limb within about 1 unit, so it needs no extra limb. When X is within the error of a multiple of 64·ln 2, either neighboring k is valid, as (k, 1.000…) or (k − 1, 0xFFFF…). `exp_dyn_entry(x, m: u64, out)` is the reduced core. It takes bit-burst e^x − 1 for a fraction x·2^(−64(m + x.len())) < ln 2 and returns the zero limbs above `out`. It processes x's top bit, then chunks of its remaining bits, combined as (1 + a)(1 + b) − 1. Each chunk spans [s, ~2s) of its own offset s, except that the first one is at least `DYN_EXP_CHUNK_MIN_BITS` wide (near x's top the factorial, not the offset, sets the term count, so narrow chunks cost as much as wide ones). `chunk_bits` extracts and normalizes every chunk's bits into one pre-sized scratch buffer up front. One generic routine, `exp_series::<E, H>`, sums every series and finalizes it directly into its slot below its leading zero limbs: an Engel tree when the bits are a single 1 (the top bit is that case, at its exact shift), otherwise a Hyper tree. Each series is sized by its own leading zeros, so only the accumulator carries the slack limb for a top bit on a limb boundary. The top bit's series runs on its own, straight into the result. Every chunk then fills its own slot (Σ bl limbs from a single scratch acquisition, never per-thread buffers), serially or on rayon, and the slots combine in chunk order, so both paths give bit-identical output. The parallel decision is made once per call: `chunks >= 2 && chunks * v >= DYN_EXP_CHUNK_PAR_WORK` on a pool of two or more threads, with `v` the result's working limbs. Precision alone predicts badly, because leading zero limbs (m > 0) shrink per-chunk work. Both knobs are plain constants in `mod.rs`, with no runtime override. `exp_static_entry::<N>` is the stack-only twin and needs `out.len() + 3 <= N` (otherwise `Err(CapacityError)`); m and x.len() are unconstrained. That is the floor for an accurate result: each series needs one guard limb past out, static finalize needs 2 more, and the guard limb absorbs finalize's last-limb rounding. It uses the same frame and schedule (`STATIC_EXP_CHUNK_MIN_BITS`), with `[u64; N]` buffers, `StaticNodeEngel`/`StaticNodeHyper` through the same `exp_series`, and `hi_mul_static` in `exp_combine`, which takes the high-product function as a parameter. `exp_chunk_static` evaluates one chunk end to end. Once `chunks >= 2 && chunks * v >= STATIC_EXP_CHUNK_PAR_WORK` (at most 64 chunks, on a machine with two or more CPUs), each chunk gets its own scoped thread with a `static_split_stack(N)` stack while the caller's thread sums the top bit's series. Results join and combine in chunk order, so the serial and threaded paths agree bit for bit. Only the threaded path touches the heap, through std's thread and join packets, as `ln2_static` does. `exp_static_entry` matches `exp_dyn_entry` exactly on almost every input; the rest differ by 1 in the last limb, and both stay within 1 ulp of the truth. `Exp` and `exp_terms` are `pub` so `benches/bin_split_cutoffs.rs` sums the same series. See the exp section of `docs/bin_split_cutoff_tuning.md`.

  `ln_dyn(x, m: i64, out)` is the public ln X, taking X as `exp_dyn` does. It writes o with |ln X| = o·2^(64k), o ∈ [1, 2^64) and `out`'s top limb its integer part, and returns (k, negative). X = 1 zeroes `out` and returns (0, false), and X = 0 returns `Err(LnError::Zero)`. `ln_reduced` (shared through `fn` pointers like `exp_reduced`) normalizes X to u = X·2^-e ∈ [1, 2), except that X ∈ [1/2, 1) stays u = X with e = 0, since −ln 2 + ln 2X would cancel |ln X|'s leading bits without bound for X just below 1. δ = |u − 1| comes straight from x's limbs (`Delta`, with 1 − u = !f + 1 exact through f's lowest nonzero limb). It takes j = floor(A·log2(64·out.len())) square roots (`DYN_LN_SQRT_A`/`STATIC_LN_SQRT_A`), less the bits by which u already sits near 1, so an input near 1 skips them. Each is one `sqrt_approx_*` of a (fl + 2)-limb radicand 4y·B into an (fl + 1)-limb root, shifted right 33 bits (pi_root's half-limb trick), the same for every y ∈ [1/2, 2). Then it runs the core on δ_y = |y − 1| (o + 1 limbs when e = 0, so the 2^j shift keeps every bit) and recovers |ln X| = 2^j·L, or |e·ln 2 ± 2^j·L| through `ln2_multiple` (ln 2 at o + 2 limbs times |e| < 2^70, at o + 1 fraction limbs). `ln_dyn_entry(x, m: u64, neg, out)` is the reduced core: |ln(1 ± δ)| for δ = x·2^(−64(m + x.len())) < 1 (δ ≤ 1/2 when neg), returning the zero limbs above `out` as `exp_dyn_entry` does, with the same extra-limb frame (`ln_frame`). ln(1 ± δ) = 2 atanh(z) with z = δ/(2 ± δ). Chunks split z, not z², because atanh has an addition rule and ATanh(z²) doesn't: atanh(z) = atanh(a) + atanh((z − a)/(1 − za)). `ln_chain` keeps the residual as a fraction n/d updated by n −= a·d, d −= a·n, two short×long `hi_mul` products, so neither z nor any residual is ever divided out. A chunk's bits come from one short division of n's and d's top limbs, sized by the chunk (`chunk_quotient`), with d rounded up so a ≤ z and n stays ≥ 0. The residual's top bit is found exactly (`mant_ge`). The first chunk is that top bit, summed as BBP `ATanh` with `Shift(2k)`. Every later chunk spans [s, ~2s) from the residual's actual top bit, exp's width rule (`chunk_width`, `DYN_LN_CHUNK_MIN_BITS` once), as a Hyper `ATanh` over A² with shift 2k, or BBP again when A = 1. Each chunk adds 2a exactly (`add_chunk`) and 2a·ATanh(a²), its series sized by its own leading zeros (`ln_chunk`, terms from `ln_terms`, the tail bound x^N/((2N+1)(1−x)) by binary search) and multiplied back by A (`mul_shr`). The chain stops once the residual's top bit passes ⌈64w/3⌉ + 2 (and the top chunk's), where its cubic term is below the frame, and the tail 2n/d is one `ratio_to_fraction_*`. So nothing is divided between chunks, and the results simply add. The dynamic core runs the chain serially (its products are cheap), then every series into one scratch acquisition, serially or on rayon (`DYN_LN_CHUNK_PAR_WORK`), alongside the tail through `join2`; the two paths agree bit for bit. `ln_static_entry::<N>` needs N ≥ out.len() + 3 (m and x.len() unconstrained). Its chunks come from the serial chain, so threads start as the chain finds them (`static_split_stack(N)` stacks, at most 64, decided from the predicted chunk count), while the caller sums the top chunk and the tail. `ln_static::<N>` needs N ≥ out.len() + 4, which covers ln 2's o + 2 limbs past its table. It takes the square roots only when N leaves them room, as they are only an optimization. With exp's squares, `ln_dyn` takes 1.2–2.1× `exp_dyn`'s time on one thread from 1 to 16384 limbs; on 12 threads 1.1–2.1×, except about 0.92× at 128–512 limbs, where exp's chunks run in parallel without squares. `ln_dyn_at`/`ln_static_at` take A explicitly for tests and `cargo bench-bin-split ln`; `ATanh` and `ln_terms` are `pub` like `Exp` and `exp_terms`. The chunk-width and parallel knobs are still `// GUESS`.
- **`consts/`** — Constant caches. `ln2_dyn` and `pi_dyn` copy requests of up to their table's length (1024 limbs) from the same compile-time tables as the static caches, without a lock. Past it they share one growable cache, a `DynCache<T>` (the series nodes plus the constant with one guard limb) behind an `RwLock`, run by `cached`: a hit copies the top limbs, and a miss takes the nodes, extends them through the constant's build function and keeps the longer result. The first request past the table therefore builds the series from scratch, and later ones extend it. Nothing under the lock can panic halfway, so a poisoned lock is used as is. `ln2_dyn` extends four base-64 BBP series summed from n = 0 (`Ln2S<A, B>`, q = A n + B, `Shift(6)`), ln 2 = 2/3·S(6,1) + 1/24·S(6,5) + 1/72·S(2,1) + 1/384·S(1,1). Each weight is 2^-k/d with d = 3 or 9 (`LN2_W`): `ln2_share` scales a copy of the top limbs of the node's Q (all that finalize reads) by d, folds 2^-k and the tree's 64^-(n+1) into the finalize shift, and finalizes, and the four shares are added. Each share is extended and finalized (`ratio_to_fraction_dyn`) in its own task. `ln2_static::<N>` copies requests of up to 1024 limbs from `consts/ln2.bin` (little-endian limbs of `ln2_dyn`'s output one limb past the table, less that limb, so `examples/gen_ln2.rs` builds the series rather than copying the old table; decoded to a `[u64]` static at compile time, and the table size comes from the file length). Past that it sums the series from scratch with `StaticNodeBBP` at one guard limb past `out` and needs `N >= out.len() + 3`, returning `Err(CapacityError)` below that. The crate-internal `ln2_static_unguarded` skips that guard limb (needing only `out.len() + 2`, and possibly a few ulps low), for `exp_static`, which keeps its own guard bits. `pi_dyn` caches π from one Chudnovsky Hyper series (`Pi`, p(n) = (13591409 + 545140134n)·r(n), which fits u128 below about 9.6M terms): `pi_denominator` truncates Q·2^(15t) and P together to one limb past the output (a common scale cancels in the ratio) and forms T = 13591409·Q′ − P′, and it finishes with one `sqrt_approx_dyn` (`pi_root`), one product and one `div_dyn`, writing floor(π·2^(64(len − 1))). `pi_static::<N>` copies requests of up to 1024 limbs from `consts/pi.bin` (written the same way by `examples/gen_pi.rs`). Past that `pi_static_sum` (which tests call directly to skip the table) sums the series from scratch with `StaticNodeHyper` and needs `N >= out.len() + 3` (otherwise `Err(CapacityError)`, before touching `out`). It goes through the same `pi_denominator`, then finishes without the 2F-limb numerator, which wouldn't fit N: V = Q′/T′ through `ratio_to_fraction_static`, then π = 426880·√10005·V as one `hi_mul_static`, whose overflow limb is π's integer part. It matches `pi_dyn` exactly. `bin_split_extend` grows a cached node with `last = false` trees, since a Hyper node built as last drops the R a later merge needs. The dynamic caches go parallel (rayon) when new·(cached² + HALF²) ≥ CUTOFF·HALF² in output limbs (`cache_par`, `DYN_LN2_PAR_*`, `DYN_PI_PAR_*`): extending also merges into the cached nodes and finalizes at the full length, so a few new limbs on a large cache still pay. Past the 1024-limb tables that makes every ln 2 build parallel, and π's from about 7 new limbs. ln 2 runs its four shares with nested `join2`. π spawns its series into the pool with `rayon::in_place_scope`, where the tree's top merges can run in parallel (`merge_par` needs a worker), while the calling thread builds the root, so the root's FFT plans stay in the caller's thread-local `FFT_CACHE` (on a worker they cost small warm extensions 4–20%). The static caches use `static_jobs`, which runs an array of jobs that each return a `[u64; N]`, on scoped threads with stacks sized from `N` (from `STATIC_LN2_PAR_CUTOFF`/`STATIC_PI_PAR_CUTOFF` limbs, falling back to the caller when a thread can't start) or in turn on the caller, without touching the heap. ln 2's four jobs each sum and finalize one series, and π's two are the series through V and the root. Static splits can't run on rayon workers, because a split needs about 640 bytes of stack per limb of `N` (`bin_split::static_split_stack` sizes the threads), which is more than a 2 MiB worker can hold at large `N`, and work stealing can put a second split on the same stack. Below the cutoffs, the parallel overhead (about 15–20 µs to wake rayon's workers, about 60 µs for four threads) costs more than the work. See the constant-caches section of `docs/bin_split_cutoff_tuning.md`.
- **`utils.rs`** — Buffer helpers: `trim_lz`, `add_buf`, `sub_buf`, `cmp_buf`, `eq_buf`, `combine_u64`, etc.
- **`mod.rs`** — Algorithm cutoff constants and `ScratchGuard`, a thread-local RAII scratch-buffer pool that reuses allocations across recursive calls (`get_splits` carves one acquired buffer into several disjoint mutable slices). `DIV_KNUTH_CUTOFF` controls when NR becomes eligible, while `BZ_CUTOFF` controls BZ's recursive Knuth base case and bypasses BZ block setup for non-NR choices below that width; `BZ_TOP_PADDED_COST_SCALE` tunes BZ's top block. Division and division-with-remainder retain independent dynamic/static BZ-vs-NR cost-model families. Reciprocal dispatch instead has one integer Knuth/NR precision cutoff per allocation model. Multiplication and NTT parallelization retain their separate cutoff families; the multiplication crossovers, including the separate dyn and static high-product cutoffs (`DYN_`/`STATIC_PARTIAL_MUL_CUTOFF`, `DYN_`/`STATIC_PARTIAL_SQR_CUTOFF`), come from `benches/mul_cutoffs.rs` (see `docs/mul_cutoff_tuning.md`). Square root has one recursive `ZIMMERMAN_SQRT_LEAF_CUTOFF` shared by both allocation models plus a binomial/Zimmermann top-level cutoff per output mode (rem, only, approx) and allocation model; static values assume `N` close to `x.len()` (see `docs/sqrt_cutoff_tuning.md`). Constants marked `// GUESS` need measurement via `cutoffs_bench`.

### Algorithm dispatch in multiplication

There are two dispatch paths, each with different algorithm sets:

**Dynamic path** (`mul_dyn` → `mul_vec`): used by heap-allocated `UBitInt`/`BitInt`.
1. `s == 1` → `mul_prim` (single-limb, asm)
2. `s == 2` → `mul_prim2` (two-limb 128-bit, asm)
3. Small → `mul_buf` (schoolbook, asm inner loop)
4. Medium → Karatsuba (recursive with chunking for unbalanced)
5. `output_limbs ≤ 2^16` → FFT (real FFT via `rustfft`, 16-bit decomposition to stay within f64 precision)
6. Large → NTT

**Static path** (`mul_static<N>` → `mul_arr<N>`): used by `UBitIntStatic<N>`/`BitIntStatic<N>`.
Same tiers except FFT is skipped; jumps directly from Karatsuba to NTT.

Squares: `sqr_dyn` is School (`sqr_buf`, ≤ `KARATSUBA_SQR_CUTOFF`) → Karatsuba (`karatsuba_sqr_entry_dyn`, ≤ `FFT_SQR_CUTOFF`) → FFT → NTT, and `sqr_static` School → Karatsuba (≤ `STATIC_NTT_SQR_CUTOFF`) → NTT. Both Karatsuba square entries take one level at any length from 6 (at 3 and 5 `karatsuba_sqr_core`'s cross term doesn't fit `out[half..]`) with leaves at `KARATSUBA_SQR_CUTOFF`. High products take `hi_*_buf` up to `DYN_PARTIAL_*_CUTOFF`/`STATIC_PARTIAL_*_CUTOFF` and the guarded truncated product (`hi_mul_guarded_dyn`/`_static`, `hi_sqr_guarded_dyn`/`_static`) above.

The `is_school` and `is_karatsuba` boundary functions use the float cutoffs (`KARATSUBA_CUTOFF`, `FFT_KARATSUBA_CUTOFF`, etc.) to compute 2D boundaries over `(long_len, short_len)` space — not simple size thresholds. `is_school_at` takes its cutoffs explicitly, as `is_karatsuba` does. Neither formula fits the measured boundary shape by shape (see `docs/mul_cutoff_tuning.md`, which also proposes a refit of `is_school`), so their constants minimize the mean time lost over a grid of shapes.

The cutoffs were retuned after the row-wise schoolbook kernels with `benches/mul_cutoffs.rs`, which forces each side through the library's own entries (`karatsuba_core`, `chunking_karatsuba`, `karatsuba_sqr_entry_dyn`, the guarded high products, `hi_*_buf_cols`/`hi_*_buf_by_rows`, and the transform entries), and `benches/mul_cutoffs.py`, which builds three code layouts, runs pinned (or, for the static NTT families, all-threads) processes and analyzes them. Nanosecond-scale crossovers get 24 processes and an exact Wilcoxon test per shape; microsecond-scale ones a few processes and averages (`--simple`). Karatsuba's own cutoffs are measured on a build whose leaves are schoolbook (`build --set ...`), then once more at the result. See `docs/mul_cutoff_tuning.md`.

### NTT implementation

NTT uses Montgomery modular arithmetic over three NTT-friendly primes (P1, P2, P3 in `mul.rs`), then reconstructs the true product via CRT. This avoids precision loss for large multiplications.

Twiddle factor tables come in two variants:
- `StaticNTTTwidles<N, P>` — compile-time fixed size, used by the static path
- `DynNTTTwidles<P>` — runtime-computed, cached in thread-local `HashMap<usize, DynNTTTwidles<P>>`

NTT supports radix-2, radix-3, and radix-5 butterflies to handle transform sizes that are smooth 5-smooth numbers.

**Previously-known source bugs, now fixed**:
- `karatsuba_entry_dyn`'s chunking path panic (`lhs must be longer then rhs` from `add_buf`) — **fixed**. Root cause: `chunking_karatsuba`'s last-chunk remainder can be up to `2*short.len()-2` limbs, landing at the exact Chunking/Recurse dispatch ratio boundary. The resulting `karatsuba_core` call needs its output buffer to be `>= 3*half+1` limbs (`half = ⌈a.len()/2⌉`) for its cross-term reconstruction (`add_buf(&mut out[half..], &cross)`), which exceeds the standard `a.len()+b.len()-1` sizing convention by 1-2 limbs whenever `b.len()` is only just above `half` — a generic gap in `karatsuba_core`'s Recurse path, not specific to chunking. Originally fixed by redirecting through a `3*half+1` scratch buffer. The current `karatsuba_core` instead adds the part of `cross` that fits in `out[half..]` and folds its carry and the first omitted limb into the one legitimate overflow limb (higher omitted limbs are provably zero by the a.len()+b.len() product-size bound), so `find_karatsuba_scratch` reserves no extra space for it. Fixing this exposed a second, independent, previously-latent bug: `karatsuba_mul`'s `Prim`/`Prim2` dispatch arms called `mul_prim`/`mul_prim2` on the *full* `out` slice rather than truncating to `long.len()`, so any caller passing a wider `out` (which the sizing fix above newly does, for nested `a1×b1` sub-calls) fed whatever stale scratch-pool garbage sat beyond `long.len()` into the multiply as if it were part of the multiplicand — silent corruption, not a panic, and only reachable when the scratch pool happened to hold nonzero leftover data from an earlier call. Fixed by truncating to `long.len()` before the multiply and explicitly zero-filling/folding any excess. Regression tests: `test_karatsuba_entry_unbalanced`, `test_karatsuba_core_recurse_boundary_sizing` (engineers the exact last-chunk boundary ratio), `test_karatsuba_entry_unbalanced_random_sweep`, `test_karatsuba_mul_prim_dispatch_ignores_stale_out_tail` (poisons `out`'s tail explicitly). Verified via an independent Python differential-fuzz model (tens of thousands of trials) before porting to Rust — worth doing again for any future change near `karatsuba_core`'s buffer arithmetic, since two of these three bugs produced *silently wrong results*, not panics, and are easy to reintroduce with a plausible-looking size-only fix.
- `powi_dyn_entry(&[3], 0, &mut out)` — **fixed**. Root cause confirmed: `powi_sz` returned `(0, 0)` for `pow == 0`, so callers allocated an empty output and `powi_dyn_entry`'s `out[0] = 1` indexed out of bounds. Fix: `powi_sz` special-cases `pow == 0` to return `(1, 1)`.
- `powi_dyn_entry(&[3], 1, &mut out)` — **fixed**. Root cause was more precise than "one step too high": bit 0 of `reverse_pow(pow)` was *always* 1 for every `pow` (an artifact of `pow`'s own leading bit leaking into the construction), forcing an unwanted multiply on the first step of every call, with the real exponent bits all landing one position higher than intended. Fixed by rebuilding `reverse_pow` directly from `pow`'s rest-bits (`pow - (1 << pow.ilog2())`) reversed into a `k`-bit field with a sentinel at position `k`, instead of the old shift-and-reverse-all-64-bits trick. This changes how many src/dst swaps `powi_dyn_core`/`powi_static_core` perform, so the parity check in `powi_dyn_entry`/`powi_static_entry` that decides which buffer starts as the answer flipped too (`% 2 == 0` → `% 2 == 1`) — the two changes only work together. Verified exhaustively (`test_powi_dyn_entry_small_exponents_exhaustive`) against a repeated-multiplication oracle across every exponent bit-length/popcount combination up to 20.
- Static `bin_split` nodes panicking at large leaf cutoffs (`StaticNodeBBP`'s "a leaf's P and Q * 2^(shift * terms) must fit N limbs" assert; an index-out-of-bounds in `push` for `StaticNodeEngel`/`StaticNodeHyper`) — **fixed**. Root cause: static merges drop low limbs to stay within `N` (`hi_mul_drop`), but leaves build some products exactly into `[u64; N]`. These are BBP's P and `Q * 2^(shift * terms)`, which must share a scale because its node has no exponents, plus Engel's Q and Hyper's Q, and also Hyper's R when x = 1. A leaf whose range was too large for `N` overflowed, so whether a cutoff worked depended on `N`, the leaf's position and the series, even though every cutoff is mathematically valid. Fixed without touching the kernels, node layouts, `Node` trait or `bin_split_tree`: each static `leaf` checks a conservative bit-length bound (`leaf_fits`, using `prod_fits`, which relies on `bitlen(xy) <= bitlen(x) + bitlen(y)`) and, when the bound fails, splits at the midpoint and merges. Leaves therefore stay exact and only merges drop limbs, the same as a smaller cutoff. The exact-leaf bodies are `#[inline(never)]` so the recursive frames don't carry unused `[u64; N]` buffers. Static parts now have bit exponents and BBP's Q no longer carries the shift, so a single BBP term always fits (`test_static_bbp_shift_past_n`). Regression tests: `test_static_large_leaf_regressions` (the exact panicking leaves), `test_static_nodes_any_cutoff` (single-term leaves, two-term leaves, the default cutoffs and single-leaf `u64::MAX` limbs at N = 4–64), `test_static_leaf_size_sweep` (every single-leaf size through and past the bound, so a bound that undercounts panics right at the boundary). The old tests missed this because they only built deep trees with small leaves.
- `karatsuba_core` silently wrong products (`mul_dyn`, `mul_static`, `karatsuba_entry_*`, and therefore `hi_mul_dyn`) — **fixed**. Root cause: `karatsuba_mul(a1, b1, z2)` returns the product limb at index `z2.len()`, but the cross-term correction subtracted it at `cross[buf_len(z2)..]`, which is lower whenever z2's top limb is zero. The squaring twin `karatsuba_sqr_core` already used `z2.len()`. Triggers: both operands with an all-zero low half (e.g. `[0; 20] + [1 << 58]` squared, at sizes ≥ 19), and structured real operands whose sub-products land a zero top limb deep in the recursion (found via `ratio_to_fraction_dyn` → `hi_mul_dyn` in `exp_dyn`). Random operands almost never hit it (probability ~2^-64 per sub-product), so every random-data test passed. Regression tests: `test_karatsuba_core_overflow_offset_zero_top`, `test_karatsuba_structured_operands` (embedded 151×151 pair), and `test_mul_structured_operand_fuzz`, which biases limbs toward zeros and powers of two and caught 571 bad products in 6000 trials with the old offset. Oracles for big-number tests should use schoolbook `mul_buf`, not `mul_dyn`.
- `hi_sqr_buf(&[], ..)` subtract-with-overflow panic — **fixed** with an empty-input guard matching `hi_mul_buf`. `test_karatsuba_static_chunking_scratch_fallback` also asserted a stale `find_karatsuba_scratch(150, 50) > 199` left over from the scratch-redirect design; the true requirement is 178, and the test now uses `N = 177` so the static fallback actually runs.
- `rcp_dyn`/`rcp_static` (NR path) breaking the `< B` error contract from `R = 727` (multi-limb errors, growing with `R`; first `R ≡ 7 mod 8`, then most sizes past ~1450) — **fixed**. Root cause was in `hi_mul_dyn`/`hi_mul_static` (and the `hi_sqr_*` twins), not the Newton code: above `PARTIAL_MUL_CUTOFF` they truncated each operand to exactly `out.len()` limbs, and the dropped partial products are worth up to ~2B ulps, i.e. the whole low output limb was wrong (`hi_mul_buf` is within a few ulps). A Newton step squares its input error, so one untruncated refine step (`q` even) with `p > 90` injected ~B ulps that grew 1 → 2 → 4 → 8 limbs over the remaining steps and outran the two guard limbs; odd `q` steps drop the correction's low limb and hid it, hence the `R`-parity pattern. Fixed by keeping `HI_MUL_GUARD_LIMBS = 2` operand limbs below the window (≤ 1 ulp error). The core product stays at its old unguarded size and `add_hi_guard_terms` adds the guard limbs' terms with linear `add_mul` passes, because simply widening the core can push it past an FFT/NTT transform size (measured up to ~2× slower at power-of-two `n`). Static entries clamp the guard (`hi_mul_static_guard`) so the split paths' low buffers still fit `N`; since operands have at most `N` limbs, the clamped guard still keeps them whole from `out.len() = N - 1`, so those windows are exact. Cost: ≈ +1–4% on `hi_mul_*`/`hi_sqr_*`, ≈ +0–1% on `rcp_dyn`/`div_dyn` at most sizes. Regression tests: `test_nr_reciprocal_high_precision_regressions`, `test_nr_reciprocal_static_high_precision_regressions`, `test_hi_mul_truncation_error_is_a_few_ulps` (the old test tolerated a fully wrong low limb, which is how this slipped through), `test_hi_mul_guard_terms_match_exact_window`, `test_hi_mul_static_near_capacity`.
- `hi_mul_static` panicking (`range end index N + 1 out of range`) at `out.len() == N` with two `N`-limb operands, even `N` — **fixed**. Root cause: the split path computed its `l1 * s0` cross term into `tmp2[..l1.len() + s0.len()]`, and for even `out.len() = N` the window width `k = N + 1` is odd, so `l1` gets one more limb than `s1` and `l1.len() + s0.len() = short.len() + 1 = N + 1`. Fixed by keeping that product's top limb out of the buffer and adding it into `out` separately, as the `l0 * s1` term already did. The guard clamp had a second term (`N - out.len() - 1`) that only existed to dodge this overflow, and it left `out.len() = N - 1` with no guard at all (a whole wrong low limb, the same bug as above); dropping it makes that window exact. `bin_split`'s static merges (`hi_mul_from`) call `hi_mul_static` with up to `N` output limbs, which rely on those exact windows. Regression test: `test_hi_mul_static_near_capacity` (`N` ∈ {96, 97, 160, 161, 512}, `out.len()` from `N - 4` to `N`, requires exact windows at `N - 1` and `N`).
- `div_dyn`/`div_static` (NR path) returning a quotient one too small — **fixed**. Root cause: `nr_refine_quo` measures err = d·y − n with a middle product, which drops the carries from the product's columns below the band: up to about (h + 1)·B at its base (the school middle product adds back only the column just below; the dyn FFT/NTT and static NTT ones drop them all). The band used the raw top window of d, so turning it into quotient units scaled that carry by B / (d's top limb), and at an odd quotient width (q_len − 2h = −1) the band's base lines up with the estimate's top guard limb, which the `Exact` verdict trusts. An exact division by a divisor with top limb 0xb came out 9·B⁻¹ low, its guard limb read u64::MAX − 8, and NR returned that floor without correcting it. Fixed by forming the band from the normalized windows of d·2^sh and n·2^sh, and the correction from the reciprocal of d·2^sh before its shift (x_norm·err_norm = x·err), which bounds the dropped carry at about 2(h + 1) ulps of the second guard limb. `div_rem` was unaffected, as its windowed finish always corrects. No measurable cost. Regression test: `test_nr_exact_division_small_top_divisor` (exact divisions with divisor top limbs 1 to 2^20 at odd quotient widths 9–739, dyn and static, including the static NTT middle product from h + 1 = 200). Before the fix, half of its cases from q_len = 201 failed.
- `ntt_mid_mul_dyn`/`ntt_mid_mul_static` returning limb 1 off by about 2^60 — **fixed**. Root cause: `ntt_mid_accumulate_scaled` reads the two convolution coefficients below the band (`res2[lo-1]`, `res3[lo-2]`), and each prime's transform was sized for `2n-1` coefficients, which wraps the product's top columns (up to `3n-3`) onto exactly those two. Where the three primes picked the same size the wrap was consistent and only disturbed limb 0, but where `2n-1` was an NTT size for some primes and not others (2n − 1 = 81, 125, 243, 375, 405, 625, 1125, 1215 below n = 700), the CRT combined residues that disagreed. Fixed by sizing every prime's transform for `2n+1` coefficients (`mid_ntt_size`), as `fft_mid_mul` already did, so nothing wraps onto a coefficient the accumulation reads. The largest transform grows at about 1% of sizes from 672 to 4096 limbs, by at most 8%. Regression test: `test_ntt_mid_mul_exact_size_transform` (those n, dyn and static, plus the static zero-padded path). Every n from 3 to 1500 is now within the documented error.

Run `cargo test --lib` to see current pass/fail status. A `test_ntt_sqr_entry_dyn_parallel_branch` failure under full-suite parallelism is a known flake; rerun it alone before suspecting a regression.

### Compile-time constraints

Avoid `u128` arithmetic in `const fn` contexts — it significantly increases compile times. Use `u64` or split operations instead.
